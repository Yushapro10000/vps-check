# vps-check

Скрипт для проверки VPS при покупке: мощность (CPU/RAM/диск), скорость и пинг до РФ, репутация IP/ASN, доступность сервисов, DNS/DPI, безопасность, исходящие порты, скорость по Ookla Speedtest. Результат сохраняется в файл — см. раздел «Отчёты: -o и -m». В интерактивном режиме скрипт может предложить установить fail2ban — только с твоего согласия.

## Установка одной командой

Скачать и сразу запустить (пункты 1-10, 13-15 подряд):

```bash
bash <(curl -sL https://raw.githubusercontent.com/Yushapro10000/vps-check/main/vps-check.sh)
```

Или через wget:

```bash
bash <(wget -qO- https://raw.githubusercontent.com/Yushapro10000/vps-check/main/vps-check.sh)
```

Запускай именно в такой форме, а не `curl ... | bash`: при пайпе у скрипта нет терминала на вводе, и интерактивные вопросы (см. ниже) молча пропускаются.

## Установка как команда

Чтобы потом просто вызывать `vps-check` без повторного скачивания:

```bash
curl -sL https://raw.githubusercontent.com/Yushapro10000/vps-check/main/vps-check.sh -o /usr/local/bin/vps-check && chmod +x /usr/local/bin/vps-check
```

Дальше:

```bash
vps-check                          # пункты 1-10, 13-15 подряд (11 и 12 — вручную, см. ниже)
vps-check 3                        # только пункт 3
vps-check 2,4,5-7                  # несколько пунктов сразу: 2, 4, 5, 6, 7
vps-check 11 example.com           # SSL-проверка конкретного домена
vps-check 12                       # только Geekbench
vps-check 14                       # только Nmap outbound
vps-check 15                       # только Ookla Speedtest
vps-check -o report.txt 9          # сохранить чистый TXT-отчёт
vps-check -m report.md 9           # сохранить форматированный Markdown-отчёт
vps-check -o rep.txt -m rep.md 0   # оба отчёта сразу
vps-check -y 9                     # без интерактивных вопросов (tmux, cron)
vps-check menu                     # список пунктов
```

Неизвестный или некорректный аргумент (например `vps-check 99` или `vps-check abc`) — скрипт выводит ошибку и меню и завершается с кодом 1, ничего не запуская.

Запуск без аргументов, `0`, `all` и `все` — одно и то же: общий прогон. `0` внутри списка тоже означает общий прогон, так что `vps-check 0,11 example.com` — это общий прогон плюс SSL-проверка домена.

Флаги (`-o`, `-m`, `-y`) позиций не занимают. Несколько пунктов задаются через запятую без пробелов (`3,5`); пробел отделяет только второй аргумент — домен для пункта 11. Если второй аргумент указан, а пункта 11 в выборке нет, скрипт предупредит, что аргумент проигнорирован; больше двух позиционных аргументов — ошибка.

## Вопросы при запуске

Если скрипт запущен в интерактивном терминале (и это не `menu`/`-h`/`--help`), он задаёт до двух вопросов:

1. `Кэшировать вывод и показать его ещё раз одним куском в конце? [y/N]` — на "y" после всех проверок весь лог печатается ещё раз целиком. Полезно на полном прогоне (`0`/`all`), где вывод длинный и начало легко уедет за скроллбек терминала.
2. `Сохранить отчёт в файл? [1: Нет (Enter), 2: TXT, 3: Markdown, 4: Оба]` — задаётся только если в командной строке не передан ни `-o`, ни `-m`. Файлы создаются в текущей папке с именами `vps-report-ГГГГММДД-ЧЧММ.txt` / `.md`.

Во время пункта 9 может прозвучать ещё один вопрос — про установку fail2ban, если ни его, ни CrowdSec нет в системе. Ответ по умолчанию «нет», а без ответа «y» ничего не устанавливается.

При неинтерактивном запуске (cron, `curl | bash`, перенаправленный ввод) все вопросы пропускаются: повторного вывода не будет, отчёт сохраняется только если явно передан `-o` и/или `-m`.

То же самое можно получить и в обычном терминале флагом `-y` (`--yes`, `--no-prompt`): вопросов не будет, лог не дублируется, отчёт пишется только при `-o`/`-m`. Флаг можно ставить в любую позицию.

## Отчёты: -o и -m

Флаги можно ставить в любую позицию аргументов и комбинировать. Вывод по ходу работы идёт в терминал как обычно, а файлы пишутся после завершения всех проверок.

- `-o`/`--output ФАЙЛ` — чистый текстовый отчёт: цветовые коды и прочие управляющие ANSI-последовательности вырезаются, файл читается в любом редакторе без «мусора».
- `-m`/`--md`/`--markdown ФАЙЛ` — Markdown-отчёт: сверху таблица с параметрами сервера (дата проверки, ОС, ядро, процессор и число vCPU, оперативная память, а также оценка безопасности, если запускался пункт 9, и итог Ookla — скорость загрузки/отдачи и задержка, если запускался пункт 15), ниже — каждая проверка отдельным разделом с выводом в блоке кода. Удобно вставлять в заметки или сравнивать два VPS.

Если `-o` и `-m` указывают на один и тот же файл, скрипт сразу завершается с ошибкой и ничего не запускает — иначе второй отчёт затёр бы первый.

Временный сырой лог, очищенная копия для Markdown и папка с Ookla CLI создаются в `/tmp` и удаляются при выходе из скрипта, в том числе по Ctrl+C.

## Что внутри
```
1 — YABS: CPU, RAM, диск (fio), сеть (iperf3, зарубежные точки), включает Geekbench.
2 — RU Speedtest: скорость и пинг до городов России (itdoginfo).
3 — IP Quality: ASN, risk score, доступность стриминга/AI-сервисов, блэклисты почты (check.place).
4 — Geolocation: в какой стране тебя видят Google/Netflix/Steam и др. (ipregion).
5 — Censorcheck: DNS-резолверы (DoH/DoT) на подмену + доступность сайтов, режим DPI.
6 — Bench.sh: CPU и диск, компактный вывод (Teddysun).
7 — sysbench CPU: однопоточный CPU-тест.
8 — Globalping: доступность ЭТОГО сервера с проверочных нод в РФ (ping/mtr, видно на каком хопе рвётся). Внешний IP определяется через ipify, при сбое — через ifconfig.me и icanhazip.
9 — Security Audit: SSH-конфиг (эффективные значения через sshd -T, если он доступен — обычно от root; иначе прямой разбор sshd_config и sshd_config.d/*.conf), учётные записи с пустым паролем (/etc/shadow, нужен root), firewall (ufw/firewalld/iptables/nftables — проверяется, что реально активен, а не просто установлен), fail2ban/CrowdSec (проверяется, что реально запущен через systemctl is-active), автообновления безопасности (unattended-upgrades/apt-daily-upgrade.timer или dnf-automatic.timer), проверка, нужна ли перезагрузка после обновлений ядра (/var/run/reboot-required, needs-restarting, needrestart; на оценку не влияет), список открытых портов — и в конце оценка 0-100 с вердиктом. Только чтение, кроме одного случая: если не найдены ни fail2ban, ни CrowdSec, в интерактивном режиме скрипт предложит установить fail2ban (вопрос `[y/N]`, по умолчанию «нет»). Без терминала и с флагом `-y` ничего не ставится, выводится только команда установки.
10 — Disk & FS: свободное место, использование inode, swap (его отсутствие — частая причина OOM на малых VPS; при наличии показывается vm.swappiness), разделы, смонтированные только для чтения, ошибки файловой системы в dmesg (EXT4/XFS, I/O error, read-only, corrupt), SMART-статус диска (если smartmontools уже установлен).
11 — SSL Check: срок действия и издатель сертификата для указанного домена; принимает голый домен, URL вида https://example.com/path (путь отбрасывается) и адрес с портом (example.com:8443 — проверяется именно этот порт, по умолчанию 443; IPv6 — в скобках: [2001:db8::1]:8443). Не входит в общий прогон — нужен домен вторым аргументом.
12 — Geekbench: тот же тест, что внутри YABS, но отдельно и без fio/iperf3, не входит в общий прогон — CPU уже покрыт пунктом 1.
13 — Censorcheck (geoblock): обратная сторона проверки — не банит ли сам зарубежный сервис этот IP по гео (в отличие от пункта 5, который смотрит DPI-блокировки со стороны РФ); запускается с --no-dns, чтобы не дублировать DNS-часть, которую уже прогоняет пункт 5.
14 — Nmap outbound: не режет ли сам хостер исходящий трафик на типичные порты — SMTP (25/465/587, частая причина банов на спам), DNS/DoT (53/853) и общая проверка через scanme.nmap.org (официальная тестовая цель Nmap). Цели заданы по IP и сканирование идёт с -n, поэтому сломанный DNS на VPS не маскирует результат; на каждый хост потолок 20 секунд.
15 — Ookla Speedtest: официальный Speedtest CLI от Ookla — скорость загрузки/отдачи, задержка, jitter и потери пакетов до ближайшего сервера Speedtest.net. Бинарь скачивается во временную папку и удаляется после теста, в систему ничего не ставится. Входит в общий прогон. Скачанный архив можно сверять по SHA-256 (см. раздел «Проверка архива Ookla»).
```

Каждый пункт можно запускать отдельно или несколько сразу через запятую/диапазон — номера вне диапазона 1-15 отбрасываются с предупреждением, скрипт не пытается вызвать несуществующий пункт:

```bash
bash vps-check.sh 1               # только YABS
bash vps-check.sh 5               # только Censorcheck
bash vps-check.sh 8               # только Globalping
bash vps-check.sh 9               # только Security Audit (с оценкой)
bash vps-check.sh 2,4,5-7         # RU Speedtest, Geolocation, Censorcheck, Bench.sh, sysbench
bash vps-check.sh 11 example.com  # SSL для домена
bash vps-check.sh 12              # только Geekbench
bash vps-check.sh 13              # только Censorcheck geoblock
bash vps-check.sh 14              # только Nmap outbound
bash vps-check.sh 15              # только Ookla Speedtest
```

## Как читать результат пункта 14

- `open` — порт доступен, хостер не режет.
- `filtered` — пакет ушёл, но ответа нет: хостер (или файрвол по пути) дропает пакеты. `filtered` на 25/465/587 обычно значит, что хостер режет исходящую почту.
- `closed` — пакет дошёл до хоста, тот ответил RST: служба там не слушает, но блокировки нет. Например, `closed` на 443 у scanme.nmap.org — это настройка самой тестовой цели, а не признак того, что хостер закрыл порт.

## Как читать результат пункта 15

- `Idle Latency` — задержка до выбранного сервера Speedtest в простое (jitter рядом — разброс задержки).
- `Download` / `Upload` — реальная пропускная способность канала VPS до этого сервера. Если она сильно ниже заявленной хостером — стоит повторить тест в другое время суток.
- `Packet Loss` — потери пакетов; стабильно выше нуля — плохой знак.
- `Result URL` — ссылка на результат на speedtest.net.

Ookla сам выбирает ближайший сервер, а не российский: для скорости именно до РФ смотри пункт 2. Конкретный сервер можно задать переменной окружения: `OOKLA_SERVER_ID=<id> vps-check 15` (список серверов — `speedtest -L`, если Ookla CLI уже установлен в системе).

## Проверка архива Ookla (SHA-256)

Пункт 15 умеет сверять SHA-256 скачанного архива с эталоном. В функции `ookla_expected_sha256` для версии 1.2.0 есть четыре пустые строки (x86_64, aarch64, armhf, i386). Пока они пусты, проверка пропускается, а в выводе пункта 15 скрипт сам показывает хеш скачанного архива («Полученный хеш: …»): его и нужно вписать, если доверяешь этому скачиванию. Так можно заполнить архитектуру той машины, на которой запущен скрипт. Как включить для всех четырёх:

1. Получи хеши. Лучше взять контрольные суммы, опубликованные Ookla, а если их нет под рукой — посчитать самому:

```bash
for a in x86_64 aarch64 armhf i386; do
  echo -n "$a  "
  curl -fsSL "https://install.speedtest.net/app/cli/ookla-speedtest-1.2.0-linux-$a.tgz" | sha256sum | awk '{print $1}'
done
```

2. Впиши значения в `echo ""` в соответствующих строках функции.

Хеш, посчитанный по файлу с того же сервера, защищает от подмены при следующих запусках, но не доказывает подлинность первого скачивания — по возможности сверь его с независимым источником.

При несовпадении скрипт не запускает бинарь, печатает ожидаемый и полученный хеш и завершает пункт с ошибкой. Для другой версии хеш можно передать напрямую: `OOKLA_VERSION=<версия> OOKLA_SHA256=<хеш> vps-check 15`. Для чужих скриптов (пункты 1-6, 12, 13) хешей нет: их содержимое меняется, и там остаются только HTTPS и таймауты.

## Оценка в Security Audit

Стартовая оценка 100, вычитается за каждую найденную проблему:

- Root-логин по SSH разрешён — минус 20
- Вход по паролю разрешён (или не запрещён явно) — минус 20
- Разрешён SSH-вход с пустым паролем (`PermitEmptyPasswords yes`) — минус 20
- Нет активного firewall — минус 25
- Нет активной защиты от брутфорса (fail2ban/CrowdSec) — минус 15
- Автообновления безопасности не настроены или не включены — минус 10

80+ — базовая защита на месте, 50-79 — есть незакрытые дыры, ниже 50 — сервер в дефолтном состоянии.

Если пункт 9 запущен не от root, `ufw status`, `iptables -L` и `nft list ruleset` не отдают данные, и состояние firewall проверить нельзя. Тогда минус 25 не засчитывается, а к вердикту добавляется пометка, что оценка может быть завышена. Для точного результата запускай через `sudo`.

## Ограничения, о которых стоит знать

- В смешанной выборке домен для SSL долетает до пункта 11 правильно: `bash vps-check.sh 2,11 example.com` — 11-й получит `example.com`, даже если он не единственный в списке.
- Повторы в выборке схлопываются: `bash vps-check.sh 5,2,2,1-3` выполнит каждый пункт по одному разу.
- Чужие скрипты (пункты 1-6, 12, 13) сначала скачиваются во временный файл с таймаутами (5 секунд на соединение, 30 на загрузку; curl, при неудаче — wget) и только потом запускаются. Если скачать не удалось — выводится `[!] Не удалось скачать скрипт ...`, а не пустой результат.
- Пункт 15 скачивает официальный Speedtest CLI от Ookla архивом во временную папку в `/tmp` (curl, при неудаче — wget; 30 секунд на загрузку) и удаляет её после теста. Если в системе уже есть `speedtest` от Ookla, используется он; питоновский `speedtest-cli` распознаётся и не подходит. Версия CLI задана переменной `OOKLA_VERSION` (по умолчанию 1.2.0) — если ссылка перестала работать, переопредели её без правки файла: `OOKLA_VERSION=<версия> vps-check 15`. Если для версии и архитектуры задан эталонный SHA-256, архив проверяется перед запуском, и при несовпадении бинарь не запускается (подробности — в разделе «Проверка архива Ookla»). Сам тест ограничен 180 секундами (если в системе есть `timeout`). Для запуска принимается лицензия Ookla (`--accept-license --accept-gdpr`), и CLI может создать `~/.config/ookla/`. Результат теста Ookla публикует на speedtest.net, и ссылка из `Result URL` доступна всем, у кого она есть.
- Установка недостающих утилит: sysbench и nmap пробуют apt/dnf/yum/apk/pacman по очереди (с обновлением индексов перед установкой — apt update/dnf makecache/yum makecache; pacman — без -Sy, чтобы не словить частичное обновление). Если скрипт запущен не от root, установка идёт через `sudo`; если нет ни root, ни sudo — установка даже не запускается, выводится `[!] Нет root и нет sudo — установить '...' невозможно`. Globalping ставится только через apt/dnf/brew (официальных пакетов для Alpine/Arch нет, там нужно вручную через AUR/community); без root и без sudo пункт 8 пропускается с пояснением. Если ни одного пакетного менеджера нет — выводится подсказка поставить вручную вместо тихого падения. Если sysbench (пункт 7) или nmap (пункт 14) поставить не удалось — например, нет root и sudo, — пункт печатает «не установлен, пропускаю» и не падает, остальные проверки идут дальше. Ookla CLI (пункт 15) через пакетный менеджер не ставится — см. выше.
- Команды `free`, `lscpu` и `ufw status`, вывод которых разбирает сам скрипт, запускаются с `LC_ALL=C`: иначе в системе с русской локалью заголовки (`Mem:`, `Status: active`) переводятся, и проверки ломаются.
- Установка fail2ban в пункте 9 использует тот же механизм, что sysbench и nmap (apt/dnf/yum/apk/pacman, не от root — через `sudo`). На RHEL-совместимых системах пакет лежит в EPEL, поэтому без `epel-release` установка не сработает — скрипт об этом напомнит. После установки служба включается через `systemctl enable --now`; без systemd её нужно запустить вручную. На Debian/Ubuntu sshd-jail включён из коробки, на других дистрибутивах его может понадобиться включить в `/etc/fail2ban/jail.local` — если после установки jail'ов нет, скрипт подскажет, что добавить. Если установка прошла и служба запущена, пункт 9 засчитывает защиту от брутфорса уже в этом же прогоне. Лог пакетного менеджера в отчёты не попадает: при успехе выводится одна строка, при сбое — последние 15 строк его вывода.
- Пункт 10 не устанавливает smartmontools автоматически (в отличие от sysbench и nmap): на VPS диск виртуальный и SMART обычно недоступен, ставить пакет ради пустого результата нет смысла. Если `smartctl` уже есть в системе, он используется.
- Если источник команды недоступен (сеть моргнула, 404 у скрипта) — под выводом пункта появится `[!] Пункт "..." завершился с ошибкой (код N)`, чтобы не спутать пустой результат с "всё чисто".
- Пункты 9 и 10 в начале выводят предупреждение, если скрипт запущен не от root — без root часть данных (ss -p, dmesg, iptables, nft, fail2ban-client) может быть урезана или пуста, и это не значит, что проблем нет. Отдельно про SSH: `sshd -T` обычному пользователю недоступен: `sshd` лежит в `/usr/sbin`, которого нет в его PATH, а при вызове по полному пути OpenSSH может требовать читаемые host-ключи (на Ubuntu 24.04 — `no hostkeys available`). То же возможно и от root, если в его PATH нет `/usr/sbin` (например, после `su` без `-`); запуск через `sudo` обычно это решает. Если `sshd -T` недоступен, скрипт читает `sshd_config` и `sshd_config.d/*.conf` напрямую — без учёта `Match`-блоков; параметр, которого в файлах нет, показывается как «не задано».
- Диапазон, задевающий пункт 11 или 12 (например `5-15`), выводит предупреждение в stderr, но всё равно выполняет их — 11 без домена просто попросит его и ничего не проверит, 12 запустится и займёт 5-10 минут. Если это не нужно — исключай их явно: `bash vps-check.sh 5-10,13-15`.
- В пункте 14 IP-адреса Google (MX для порта 25 и резервный адрес для 465/587) вписаны в скрипт. Релей для 465/587 сначала определяется через DNS и только при его недоступности берётся резервный IP; если Google сменит адреса, откроются порты не у того хоста — тогда результат стоит перепроверить вручную.
- Markdown-отчёт собирается по заголовкам вида `########## Название ##########` из лога. Если раздел «Результаты проверок» в `.md` оказался пустым, проверь `awk -W version`: старая сборка mawk (в Debian 12 и Ubuntu 22.04 это 1.3.4-20200120) может не понимать повторения `{10}` в регулярках. Лечится одной строкой: в функции `generate_markdown_report` замени `/^#{10} .+ #{10}$/` на `/^########## .+ ##########$/` — смысл тот же, а работает в любом awk.

## Требования

Bash, `curl`/`wget`, `tar` (для пункта 15). Отдельные пункты сами подтянут нужные утилиты (например `sysbench`, `nmap`, `globalping`) через тот пакетный менеджер, что нашёлся в системе: apt/dnf/yum/apk/pacman (и brew для globalping на macOS). Пункты 9 и 10 только читают систему; единственное исключение — предложение установить fail2ban в пункте 9, оно выполняется только после явного согласия. Для полной картины в Security Audit (чтение sshd_config, `sshd -T`, ufw/firewalld/iptables, systemctl) скрипт стоит запускать от root/через sudo.
