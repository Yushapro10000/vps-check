# vps-check

Скрипт для проверки VPS при покупке. 16 проверок в пяти группах: сама машина (CPU, память, диск), сеть (скорость, в том числе до России, и исходящие порты), безопасность, доступность из РФ, IP и сервисы. Всё, что нужно от тебя (домен для SSL-проверки, согласие на Speedtest от Ookla, установка fail2ban, отчёт в файл), скрипт спрашивает сразу перед стартом, а дальше проверки идут без остановок. В конце — сводка по всем пунктам и, если нужно, отчёт в TXT или Markdown.

## Быстрый старт

Общий прогон — все 16 пунктов, без установки:

```bash
bash <(curl -sL https://raw.githubusercontent.com/Yushapro10000/vps-check/main/vps-check.sh)
```

Или через wget:

```bash
bash <(wget -qO- https://raw.githubusercontent.com/Yushapro10000/vps-check/main/vps-check.sh)
```

Отдельные пункты и группы — тоже без установки, аргументы пишутся после скобки:

```bash
bash <(curl -sL https://raw.githubusercontent.com/Yushapro10000/vps-check/main/vps-check.sh) net             # группа «Сеть»
bash <(curl -sL https://raw.githubusercontent.com/Yushapro10000/vps-check/main/vps-check.sh) 3-5             # пункты 3, 4, 5
bash <(curl -sL https://raw.githubusercontent.com/Yushapro10000/vps-check/main/vps-check.sh) sec,ru          # две группы
bash <(curl -sL https://raw.githubusercontent.com/Yushapro10000/vps-check/main/vps-check.sh) 11 example.com  # SSL домена
bash <(curl -sL https://raw.githubusercontent.com/Yushapro10000/vps-check/main/vps-check.sh) -m report.md 10 # с отчётом
```

Слово `vps-check` перед пунктами тоже понимается — так можно писать по привычке от установленной команды: `bash <(curl -sL …/vps-check.sh) vps-check 3-5`.

Запускай именно в форме `bash <(...)`, а не `curl ... | bash`: при пайпе у скрипта нет терминала на вводе, и вопросы перед стартом пропускаются. Если вопросы и не нужны (cron, автоматизация), пайп тоже работает: `curl -sL …/vps-check.sh | bash -s -- -y net`.

## Установка как команда

Чтобы потом просто вызывать `vps-check` без повторного скачивания:

```bash
curl -sL https://raw.githubusercontent.com/Yushapro10000/vps-check/main/vps-check.sh -o /usr/local/bin/vps-check && chmod +x /usr/local/bin/vps-check
```

Дальше:

```bash
vps-check                          # общий прогон: все 16 пунктов
vps-check net                      # одна группа: machine, net, sec, ru, ip (или по-русски: машина, сеть, …)
vps-check sec,ru                   # несколько групп
vps-check net,11                   # группа и отдельный пункт вместе
vps-check 3                        # только пункт 3
vps-check 2,4,6-9                  # несколько пунктов: 2, 4, 6, 7, 8, 9
vps-check 11 example.com           # SSL-проверка конкретного домена
vps-check -o report.txt 10         # сохранить чистый TXT-отчёт
vps-check -m report.md 10          # сохранить Markdown-отчёт
vps-check -o rep.txt -m rep.md     # оба отчёта сразу
vps-check -y 10                    # без вопросов (tmux, cron)
vps-check menu                     # список пунктов и групп
```

## Как выбрать, что запускать

Без аргументов, с `0`, `all` или `все` — общий прогон: все 16 пунктов по порядку групп. В выборке через запятую (без пробелов) можно смешивать:

- номера: `3`, `10,11`;
- диапазоны: `6-9`;
- группы по-английски или по-русски: `machine`/`машина`, `net`/`сеть`, `sec`/`безопасность`, `ru`/`рф`, `ip`/`сервисы`;
- `0`/`all`/`все` внутри списка — тоже общий прогон.

Повторы схлопываются: `vps-check net,6,6-7` выполнит каждый пункт один раз. Номера вне диапазона 1–16 и перевёрнутые диапазоны (`5-3`) отбрасываются с предупреждением, остальное выполняется. Если не осталось ни одного существующего пункта или в выборке есть непонятное слово (`vps-check foo`), скрипт выводит ошибку и меню и завершается с кодом 1, ничего не запуская.

Флаги (`-o`, `-m`, `-y`) можно ставить в любую позицию. Пробел отделяет только второй аргумент — домен для пункта 11: `vps-check sec example.com`. Если домен указан, а пункта 11 в выборке нет, скрипт предупредит, что аргумент проигнорирован; больше двух позиционных аргументов — ошибка.

Когда в запуске пункты из разных групп, перед каждой группой выводится её заголовок (`>>>>>>>>>> Сеть: скорость и исходящие порты (пункты 6-9) <<<<<<<<<<`), а в Markdown-отчёте разделы идут по группам.

## Вопросы перед стартом

В интерактивном терминале скрипт сначала задаёт все нужные вопросы — только те, что относятся к выбранным пунктам, — и коротко объясняет, зачем каждый. После этого проверки идут без остановок, и можно отойти.

1. **Домен для SSL-проверки** (пункт 11), если не передан аргументом. Нужен, если на сервере есть сайт, панель или подписка по домену. Enter — пункт пропускается с пометкой в сводке.
2. **Согласие на Speedtest от Ookla** (пункты 6 и 7), `[Y/n]`. CLI от Ookla при запуске принимает свою лицензию, а результаты сохраняются у Ookla на speedtest.net — как при обычном тесте на сайте. «n» — оба пункта пропускаются.
3. **fail2ban** (пункт 10), `[y/N]`, если защиты SSH от подбора паролей явно нет: ни fail2ban, ни CrowdSec — предложит поставить fail2ban; fail2ban стоит, но остановлен, а CrowdSec нет — предложит запустить. Ответ запоминается, и посреди прогона пункт 10 больше не спрашивает. Неочевидные случаи (например, CrowdSec работает, но без bouncer'а) пункт 10 разбирает сам и тогда спрашивает уже во время проверки.
4. **Отчёт в файл**, если не передан ни `-o`, ни `-m`: `[1: нет (Enter), 2: TXT, 3: Markdown, 4: оба]`. Файлы создаются в текущей папке: `vps-report-ГГГГММДД-ЧЧММ.txt` / `.md`.
5. **Повторить весь вывод в конце одним куском** `[y/N]` — только если пунктов несколько: на длинном прогоне начало легко уезжает за пределы экрана.

Без терминала (cron, `curl | bash`, перенаправленный ввод) и с флагом `-y` (`--yes`, `--no-prompt`) вопросов нет: пункт 11 без домена в аргументе пропускается, fail2ban не ставится и не запускается, Speedtest от Ookla запускается (лицензия принимается), отчёт пишется только при `-o`/`-m`.

## Итоговая сводка, Ctrl+C и код возврата

Если в прогоне больше одного пункта, в конце выводится сводка: номер, время, название и статус каждого пункта (`✓`, `✗ ошибка (код N)`, `пропущен` — например, не удалось поставить sysbench, не указан домен для пункта 11 или ты отказался от Ookla). В длинном прогоне так сразу видно, какой пункт упал.

```
  1)  12:34  YABS — ✓
  3)   0:21  sysbench CPU — ✓
  9)   0:40  Nmap outbound — ✗ ошибка (код 1)
 12)   0:02  Globalping — пропущен

Успешно: 2, с ошибкой: 1, пропущено: 1. Общее время: 13:37
```

Если в запуске были пункты группы «Доступность из РФ», после сводки скрипт напоминает про Telegram-ботов для ручной сверки (см. раздел «Telegram-боты»).

Ctrl+C останавливает проверки, но не теряет результат: скрипт допишет сводку (прерванный пункт помечается как «прерван») и сохранит отчёты `-o`/`-m` по тому, что успело выполниться. Временная папка удаляется в любом случае. Остановка срабатывает, даже если сторонний скрипт или утилита сами ловят Ctrl+C и завершаются «нормально» (так делают YABS и nmap): каждый пункт выполняется в отдельном подшелле, и после Ctrl+C ни остаток пункта, ни следующие пункты не запускаются.

Код возврата (удобно для cron и своих обёрток):

- `0` — все пункты прошли (пропущенные ошибкой не считаются);
- `1` — хотя бы один пункт завершился с ошибкой, аргументы неверные или лог прогона не удалось записать полностью (например, кончилось место во временной папке — скрипт об этом предупредит);
- `130` — прогон прерван по Ctrl+C.

## Отчёты: -o и -m

Флаги ставятся в любую позицию и комбинируются. Вывод по ходу работы идёт в терминал как обычно, а файлы пишутся после завершения всех проверок. Если ни одного флага нет, скрипт спросит про отчёт перед стартом.

- `-o`/`--output ФАЙЛ` — чистый текстовый отчёт: цветовые коды, заголовки окна, гиперссылки и прочие управляющие последовательности вырезаются, файл читается в любом редакторе без «мусора».
- `-m`/`--md`/`--markdown ФАЙЛ` — Markdown-отчёт. Сверху таблица с параметрами сервера (дата проверки, ОС, ядро, процессор и число vCPU, оперативная память) и ключевыми цифрами из тех пунктов, что запускались: Geekbench single/multi (из пункта 1 или 4), масштабирование sysbench (3), Ookla до ближайшего сервера (6) и по городам России (7), оценка безопасности (10). Под ней — сводка по пунктам таблицей, ниже — проверки по группам, каждая отдельным разделом с выводом в блоке кода. Если прогон прервали по Ctrl+C, в шапке появляется строка «Статус прогона: прерван». Удобно вставлять в заметки или сравнивать два VPS.

Если `-o` и `-m` указывают на один и тот же файл, скрипт сразу завершается с ошибкой и ничего не запускает — иначе второй отчёт затёр бы первый.

Всё временное (сырой лог, скачанные сторонние скрипты, Ookla CLI, данные для сводки) лежит в одной папке `vps-check-XXXXXX` внутри `/tmp` (или `$TMPDIR`, если он задан) и удаляется целиком при выходе из скрипта, в том числе по Ctrl+C.

## Подробно о пунктах

### Машина (1–5)

**1 — YABS:** диск (fio), сеть (iperf3 до зарубежных точек) и Geekbench. Если в этом же запуске есть пункт 4 (например, в общем прогоне), YABS запускается без Geekbench — его делает пункт 4, чтобы не гонять один долгий тест дважды. Отдельно `vps-check 1` — полный YABS с Geekbench.

**2 — Bench.sh:** CPU и диск, компактный вывод (Teddysun).

**3 — sysbench CPU:** тест в один поток и во все vCPU со сравнением: прирост должен быть близок к числу ядер, иначе возможен оверселлинг или vCPU — это потоки SMT (ориентир, а не приговор).

**4 — Geekbench:** тот же тест, что внутри YABS, но отдельно и без fio/iperf3 — для сравнения CPU между хостерами. Занимает 5–10 минут.

**5 — Disk & FS:** свободное место, использование inode, swap (его отсутствие — частая причина OOM на малых VPS; при наличии показывается vm.swappiness), разделы, смонтированные только для чтения, ошибки файловой системы в dmesg (EXT4/XFS, I/O error, read-only, corrupt), SMART-статус диска (если smartmontools уже установлен).

### Сеть (6–9)

**6 — Ookla Speedtest:** официальный Speedtest CLI от Ookla — скорость загрузки/отдачи, задержка, jitter и потери пакетов до ближайшего сервера Speedtest.net. Ближайший сервер показывает, на что способен сам порт VPS; рядом с пунктом 7 видно, сколько скорости теряется по дороге до России. Бинарь скачивается во временную папку (за прогон один раз — пункт 7 берёт уже скачанный) и удаляется при выходе, в систему ничего не ставится. Скачанный архив можно сверять по SHA-256, но эталонные хеши в скрипте пока не заполнены: по умолчанию пункт только скачивает архив по HTTPS и целостность не проверяет (как включить — в разделе «Проверка архива Ookla»).

**7 — Ookla до РФ:** тот же Ookla Speedtest, но до серверов в Москве, Петербурге, Екатеринбурге и Новосибирске. Для зарубежного VPS ближайший сервер Ookla — не российский, поэтому серверы в каждом городе ищутся поиском speedtest.net и тестируются явно; на город — до двух серверов (популярные бывают перегружены). Нужен jq — пункт поставит его сам.

**8 — iperf3 до РФ:** скорость и пинг до городов России (скрипт itdoginfo). Ему нужны iperf3, jq, awk и ping — без них он сразу выходит с ошибкой `Required command ... not found`, поэтому недостающие утилиты пункт ставит сам перед запуском.

**9 — Nmap outbound:** не режет ли сам хостер исходящий трафик на типичные порты — SMTP (25/465/587, частая причина банов на спам), DNS/DoT (53/853) и общая проверка через scanme.nmap.org (официальная тестовая цель Nmap). Адреса почтовых серверов Google сначала берутся из DNS, а если DNS на VPS сломан — из резервных IP в скрипте; сканирование идёт с `-n`, поэтому сломанный DNS не маскирует результат. На каждый хост потолок 20 секунд.

### Безопасность (10–11)

**10 — Security Audit:** SSH-конфиг (эффективные значения через `sshd -T`, если он доступен — обычно от root; иначе прямой разбор `sshd_config` и `sshd_config.d/*.conf`), в том числе вход по паролю через keyboard-interactive + PAM, который работает даже при `PasswordAuthentication no`; учётные записи с пустым паролем (`/etc/shadow`, нужен root); firewall (ufw/firewalld/iptables/nftables — проверяется, что входящие реально фильтруются, а правила Docker, fail2ban и CrowdSec за firewall не принимаются); порты Docker-контейнеров, открытые в обход ufw/firewalld; fail2ban (запущен и есть jail для SSH) и CrowdSec (запущен и есть bouncer, который блокирует); автообновления безопасности (что они реально включены в конфиге, а не просто стоит пакет); нужна ли перезагрузка после обновлений ядра (`/var/run/reboot-required`, needs-restarting, needrestart; на оценку не влияет); список открытых портов и отдельно — базы данных, кэши и Docker API, которые слушают не только localhost. В конце оценка 0–100 с вердиктом (как считается — в разделе «Оценка в Security Audit»). Только чтение, кроме установки или запуска fail2ban — и то лишь с твоего согласия (см. «Вопросы перед стартом»).

**11 — SSL Check:** срок действия и издатель сертификата домена, сколько дней осталось (предупреждение, если меньше 14 или сертификат уже истёк), проверка цепочки доверия и совпадения имени в сертификате (самоподписанный, без промежуточного, выдан на другой домен). На подключение даётся 10 секунд, поэтому порт, закрытый файрволом, не вешает проверку. Принимает голый домен, URL вида `https://example.com/path` (путь отбрасывается) и адрес с портом (`example.com:8443` — проверяется именно этот порт, по умолчанию 443; IPv6 — в скобках: `[2001:db8::1]:8443`); для IP-адреса имя в сертификате сверяется с самим IP. Домен передаётся вторым аргументом или вводится в вопросе перед стартом.

### Доступность из РФ (12–13)

**12 — Globalping:** доступность ЭТОГО сервера с проверочных нод в России (ping и mtr — видно, на каком хопе рвётся). Внешний IP определяется через ipify, при сбое — через ifconfig.me и icanhazip.

**13 — Censorcheck DPI:** DNS-резолверы (DoH/DoT) на подмену и доступность сайтов в режиме DPI — то, что видит российский пользователь.

### IP и сервисы (14–16)

**14 — IP Quality:** ASN, risk score, доступность стриминга и AI-сервисов, блэклисты почты (check.place).

**15 — Geolocation:** в какой стране тебя видят Google, Netflix, Steam и др. (ipregion).

**16 — Censorcheck geoblock:** обратная сторона пункта 13 — не банит ли сам зарубежный сервис этот IP по гео; запускается с `--no-dns`, чтобы не дублировать DNS-часть, которую уже прогоняет пункт 13.

## Как читать результат пункта 9 (Nmap)

- `open` — порт доступен, хостер не режет.
- `filtered` — пакет ушёл, но ответа нет: хостер (или файрвол по пути) дропает пакеты. `filtered` на 25/465/587 обычно значит, что хостер режет исходящую почту.
- `closed` — пакет дошёл до хоста, тот ответил RST: служба там не слушает, но блокировки нет. Например, `closed` на 443 у scanme.nmap.org — это настройка самой тестовой цели, а не признак того, что хостер закрыл порт.

## Как читать результат пунктов 6 и 7 (Ookla)

- `Idle Latency` — задержка до выбранного сервера Speedtest в простое (jitter рядом — разброс задержки).
- `Download` / `Upload` — реальная пропускная способность канала VPS до этого сервера. Если она сильно ниже заявленной хостером — стоит повторить тест в другое время суток.
- `Packet Loss` — потери пакетов; стабильно выше нуля — плохой знак.
- `Result URL` — ссылка на результат на speedtest.net.

В пункте 6 Ookla сам выбирает ближайший сервер, а не российский: для скорости до РФ смотри пункты 7 и 8. Конкретный сервер можно задать переменной окружения: `OOKLA_SERVER_ID=<id> vps-check 6` (список ближайших серверов — `speedtest -L`, если Ookla CLI уже установлен в системе).

Пункт 7 печатает по строке на город: `Moscow — MTS: ↓ 812.4 Мбит/с, ↑ 640.1 Мбит/с, пинг 45.7 мс (джиттер 1.2 мс), потери 0.0%` (↓ — загрузка на VPS, ↑ — отдача с VPS), а в конце — короткую строку «Итог Ookla до РФ», которая попадает и в шапку Markdown-отчёта. Если первый сервер в городе отказал, пробуется второй; если город не нашёлся или ни один сервер не ответил, это видно в итоге («— нет серверов», «— не вышло»). Пункт считается успешным, если удалось проверить хотя бы один город.

Свои города — переменной `OOKLA_RU_CITIES`: через запятую, по-английски, как в базе speedtest.net; через `|` — запасные написания одного города (если по первому серверов не нашлось, ищется следующее). По умолчанию:

```bash
OOKLA_RU_CITIES="Moscow,Saint Petersburg|St Petersburg|Petersburg,Yekaterinburg|Ekaterinburg,Novosibirsk" vps-check 7
OOKLA_RU_CITIES="Moscow,Kazan,Krasnodar" vps-check 7      # свой набор
```

Каждый город — это отдельный тест до 90 секунд, так что четыре города добавляют к прогону 2–4 минуты.

## Проверка архива Ookla (SHA-256)

Пункты 6 и 7 умеют сверять SHA-256 скачанного архива с эталоном. В функции `ookla_expected_sha256` для версии 1.2.0 есть четыре пустые строки (x86_64, aarch64, armhf, i386). Пока они пусты, проверка пропускается, а в выводе скрипт сам показывает хеш скачанного архива («Полученный хеш: …»): его и нужно вписать, если доверяешь этому скачиванию. Так можно заполнить архитектуру той машины, на которой запущен скрипт. Как включить для всех четырёх:

1. Получи хеши. Лучше взять контрольные суммы, опубликованные Ookla, а если их нет под рукой — посчитать самому:

```bash
for a in x86_64 aarch64 armhf i386; do
  echo -n "$a  "
  curl -fsSL "https://install.speedtest.net/app/cli/ookla-speedtest-1.2.0-linux-$a.tgz" | sha256sum | awk '{print $1}'
done
```

2. Впиши значения в `echo ""` в соответствующих строках функции.

Хеш, посчитанный по файлу с того же сервера, защищает от подмены при следующих запусках, но не доказывает подлинность первого скачивания — по возможности сверь его с независимым источником (например, скачай с двух разных машин).

При несовпадении скрипт не запускает бинарь, печатает ожидаемый и полученный хеш и завершает пункт с ошибкой. Для другой версии хеш можно передать напрямую: `OOKLA_VERSION=<версия> OOKLA_SHA256=<хеш> vps-check 6`. Для чужих скриптов (пункты 1, 2, 4, 8, 13–16) хешей нет: их содержимое меняется, и там остаются только HTTPS и таймауты.

## Оценка в Security Audit (пункт 10)

Стартовая оценка 100, вычитается за каждую найденную проблему (ниже нуля не опускается):

- Root-логин по SSH разрешён (`PermitRootLogin yes`) — минус 20
- По SSH можно войти по паролю — минус 20. Это `PasswordAuthentication yes` (или не задано — по умолчанию yes), а также связка `KbdInteractiveAuthentication yes` + `UsePAM yes`: через неё PAM спрашивает тот же пароль, даже если `PasswordAuthentication no`. Не снимается, если `AuthenticationMethods` в каждом варианте входа требует ключ
- Разрешён SSH-вход с пустым паролем (`PermitEmptyPasswords yes`) — минус 20
- Есть учётные записи с пустым паролем в `/etc/shadow` — минус 20 (закрыть: `passwd -l <имя>`)
- Нет активного firewall — минус 25. Активным считается: работающий ufw или firewalld; в iptables — цепочка INPUT с policy DROP или правилами DROP/REJECT; в nftables — цепочка с `hook input`, где есть `policy drop` или правило drop/reject. Правила Docker (они в FORWARD), fail2ban и CrowdSec (банят отдельные IP) firewall'ом не считаются
- Нет рабочей защиты SSH от брутфорса — минус 15. Засчитывается fail2ban, у которого есть jail для SSH, или CrowdSec, у которого есть хотя бы один bouncer (без bouncer'а CrowdSec только видит атаки, но ничего не блокирует). Bouncer'ы считаются по табличному выводу `cscli bouncers list -o raw`: одна строка — один bouncer, так что новые поля в будущих версиях cscli счёт не исказят. Если формат вывода не узнан, защита не засчитывается, а скрипт просит проверить вручную
- Автообновления безопасности не включены — минус 10. Для Debian/Ubuntu смотрится `APT::Periodic::Unattended-Upgrade` в конфиге apt: сам пакет unattended-upgrades и таймер apt-daily-upgrade есть почти везде и ничего не значат. Для RHEL/Fedora — включённый `dnf-automatic-install.timer` или таймер dnf-automatic с `apply_updates = yes`
- Базы данных, кэши или Docker API слушают не только localhost (порты 2375, 3306, 5432, 6379, 9200, 11211, 27017) — минус 10

Без минуса, но с предупреждением: порты Docker-контейнеров, опубликованные на все интерфейсы (`0.0.0.0:443->443`). Docker открывает их своими правилами iptables в обход ufw/firewalld, поэтому «закрытый» в ufw порт контейнера на деле доступен из интернета. Если порт нужен только локально (за nginx/caddy или панелью), публикуй его как `127.0.0.1:ПОРТ:ПОРТ` в docker-compose; если нужна фильтрация внешних подключений — правила в цепочке `DOCKER-USER` (для ufw есть утилита ufw-docker).

Если OpenSSH-сервер не найден (нет ни `sshd_config`, ни `sshd -T`), SSH-пункты не оцениваются.

80+ — базовая защита на месте, 50–79 — есть незакрытые дыры, ниже 50 — сервер в дефолтном состоянии.

Если пункт 10 запущен не от root, `ufw status`, `iptables -S` и `nft list ruleset` не отдают данные, и состояние firewall проверить нельзя. Тогда минус 25 не засчитывается, а к вердикту добавляется пометка, что оценка может быть завышена. Для точного результата запускай через `sudo`. Списки jail'ов fail2ban и bouncer'ов CrowdSec без root скрипт пробует прочитать через `sudo -n` (без запроса пароля); если не вышло, защита засчитывается на доверии.

## Ограничения, о которых стоит знать

- Общий прогон долгий: YABS и Geekbench (пункты 1 и 4) вместе занимают 10–20 минут, Ookla до РФ (7) — ещё 2–4 минуты. Если нужна только часть — запускай группы: `vps-check net,sec`.
- В смешанной выборке домен для SSL долетает до пункта 11 правильно: `vps-check sec,ru example.com` — пункт 11 получит `example.com`.
- Чужие скрипты (пункты 1, 2, 4, 8, 13–16) сначала скачиваются во временный файл с таймаутами (5 секунд на соединение, 30 на загрузку; curl, а wget — только если curl нет или он не справился с HTTPS (если сайт недоступен или ответил ошибкой вроде 404, wget не запускается — он получил бы то же самое), и не больше двух попыток: по умолчанию wget делает их до 20, и на молчащем сайте пункт висел бы минутами) и только потом запускаются. Если скачать не удалось — выводится `[!] Не удалось скачать скрипт ...` с причиной простыми словами (домен не находится в DNS — сайт, скорее всего, закрылся; файла по ссылке нет — 404; доступ закрыт — 403; сервер ответил ошибкой; таймаут; проблема с сертификатом) и исходным текстом ошибки curl/wget, а не пустой результат. Если сервер ответил пустой страницей, это тоже сообщается отдельно. Скрипт сохраняется в файл байт в байт, поэтому работают и скрипты с нечитаемыми символами. Если по ссылке вместо скрипта пришла веб-страница (HTML/XML), скрипт сообщает об этом и ничего не запускает; если это ошибка S3-хранилища (`AccessDenied`, `NoSuchKey`), он называет её и объясняет, что файл удалён или закрыт автором. Это чужой код, который выполнится на твоём VPS, — при желании посмотри его сам перед запуском (`curl -s <ссылка> | less`). При запуске через `curl … | bash` во входном потоке лежит остаток самого `vps-check`; чтобы сторонний скрипт не «съел» его вместе со сводкой и отчётами, проверкам в этом режиме вместо stdin отдаётся пустой ввод.
- Пункты 6 и 7 скачивают официальный Speedtest CLI от Ookla архивом во временную папку скрипта (curl, при неудаче — wget, не больше двух попыток; 30 секунд на загрузку) и удаляют её при выходе. Пункт 7 дополнительно обращается к поиску серверов speedtest.net (`www.speedtest.net/api/js/servers`) — без доступа к нему города не найдутся, и пункт так и скажет. Если `/tmp` смонтирован с `noexec`, бинарь не запустится (код 126) — скрипт подскажет запуск с другой папкой: `mkdir -p ~/tmp && TMPDIR=~/tmp vps-check 6`. Если в системе уже есть `speedtest` от Ookla, используется он; питоновский `speedtest-cli` распознаётся и не подходит. Версия CLI задана переменной `OOKLA_VERSION` (по умолчанию 1.2.0) — если ссылка перестала работать, переопредели её без правки файла: `OOKLA_VERSION=<версия> vps-check 6`. Если для версии и архитектуры задан эталонный SHA-256, архив проверяется перед запуском, и при несовпадении бинарь не запускается (подробности — в разделе «Проверка архива Ookla»). Тест пункта 6 ограничен 180 секундами, каждый город в пункте 7 — 90 секундами (если в системе есть `timeout`); Ctrl+C прерывает тест сразу. Для запуска принимается лицензия Ookla (`--accept-license --accept-gdpr`), и CLI может создать `~/.config/ookla/`. Результаты тестов Ookla сохраняет у себя на speedtest.net, и ссылка из `Result URL` (пункт 6) доступна всем, у кого она есть. В интерактивном запуске скрипт спрашивает согласие перед стартом; с `-y` и без терминала пункты 6–7 запускаются — чтобы их не было, выбирай пункты без них: `vps-check 1-5,8-16`.
- Установка недостающих утилит: sysbench (пункт 3), nmap (пункт 9), iperf3, jq и ping для стороннего скрипта пункта 8 и jq для пункта 7 ставятся через apt-get/dnf/yum/apk/pacman — что найдётся, причём все пакеты одного пункта одной командой (с обновлением индексов перед установкой — apt-get update/dnf makecache/yum makecache; pacman — без -Sy, чтобы не словить частичное обновление). На Debian/Ubuntu используется `apt-get`, а не `apt`: у `apt` нестабильный интерфейс, и в скриптах он пишет в отчёт `WARNING: apt does not have a stable CLI interface`. На свежем VPS в первые минуты apt часто занят автообновлениями — скрипт ждёт освобождения блокировки (до минуты на обновление индексов и до двух минут на установку), а не падает с `Could not get lock`. Лог пакетного менеджера в отчёты не попадает: при успехе выводится одна строка, при сбое — последние 15 строк. Если скрипт запущен не от root, установка идёт через `sudo`; если нет ни root, ни sudo — установка даже не запускается, выводится `[!] Нет root и нет sudo — установить '...' невозможно`. Globalping (пункт 12) ставится только через apt/dnf/brew (официальных пакетов для Alpine/Arch нет, там нужно вручную через AUR/community): сначала подключается репозиторий packagecloud, и если он недоступен, пункт сразу говорит об этом; без root и без sudo пункт 12 пропускается с пояснением. Если ни одного пакетного менеджера нет — выводится подсказка поставить вручную вместо тихого падения. Если утилиту поставить не удалось — например, нет root и sudo, — пункт печатает «не установлен, пропускаю», в сводке отмечается как «пропущен», и остальные проверки идут дальше. Ookla CLI (пункты 6 и 7) через пакетный менеджер не ставится — см. выше.
- Команды `free`, `lscpu` и `ufw status`, вывод которых разбирает сам скрипт, запускаются с `LC_ALL=C`: иначе в системе с русской локалью заголовки (`Mem:`, `Status: active`) переводятся, и проверки ломаются.
- Установка fail2ban в пункте 10 использует тот же механизм, что sysbench и nmap (apt/dnf/yum/apk/pacman, не от root — через `sudo`). На RHEL-совместимых системах пакет лежит в EPEL, поэтому без `epel-release` установка не сработает — скрипт об этом напомнит. Если fail2ban уже стоит, но остановлен, скрипт предлагает его запустить — с той же правкой для Debian 12, потому что служба часто лежит как раз из-за неё. После установки или по согласию на запуск служба включается и перезапускается через `systemctl`; без systemd её нужно запустить вручную. На Debian 12+ по умолчанию нет rsyslog и файла `/var/log/auth.log`, из-за чего sshd-jail не находит лог и fail2ban не стартует. Если файлового журнала SSH нет, скрипт создаёт `/etc/fail2ban/jail.d/vps-check-sshd.local` с `backend = systemd` (и при необходимости ставит `python3-systemd`). На Debian/Ubuntu sshd-jail включён из коробки, на других дистрибутивах его может понадобиться включить в `/etc/fail2ban/jail.local` — если после установки jail'а для SSH нет, скрипт подскажет, что добавить. Защита от брутфорса засчитывается уже в этом же прогоне, если служба запущена и jail для SSH есть.
- Пункт 5 не устанавливает smartmontools автоматически (в отличие от sysbench и nmap): на VPS диск виртуальный и SMART обычно недоступен, ставить пакет ради пустого результата нет смысла. Если `smartctl` уже есть в системе, он используется.
- Если источник команды недоступен (сеть моргнула, 404 у скрипта) — под выводом пункта появится причина или `[!] Пункт "..." завершился с ошибкой (код N)`, чтобы не спутать пустой результат с «всё чисто».
- Пункты 10 и 5 в начале выводят предупреждение, если скрипт запущен не от root — без root часть данных (ss -p, dmesg, iptables, nft, fail2ban-client) может быть урезана или пуста, и это не значит, что проблем нет. Отдельно про SSH: `sshd -T` обычному пользователю недоступен — OpenSSH требует читаемые host-ключи (на Ubuntu 24.04 — `no hostkeys available`). Если `sshd` нет в PATH (например, после `su` без `-`), скрипт сам пробует `/usr/sbin/sshd`. Если `sshd -T` всё равно недоступен, скрипт читает `sshd_config` и `sshd_config.d/*.conf` напрямую, как это делает сам sshd: берётся первое найденное значение, а строки внутри `Match`-блоков пропускаются (они действуют только для части подключений). Параметр, которого в файлах нет, показывается как «не задано» вместе со значением OpenSSH по умолчанию.
- В пункте 9 адреса Google (MX `gmail-smtp-in.l.google.com` для порта 25 и релей `smtp.gmail.com` для 465/587) сначала определяются через DNS, и только если DNS недоступен, берутся резервные IP из скрипта. Если Google сменит адреса, а DNS на VPS сломан, проверятся порты не у того хоста — тогда результат стоит перепроверить вручную.
- Проверке Docker в пункте 10 нужен root или членство в группе `docker`; если Docker стоит, но демон не запущен, проверка пропускается с пояснением.
- Markdown-отчёт собирается по заголовкам вида `########## Название ##########` (пункты) и `>>>>>>>>>> Группа <<<<<<<<<<` (группы) из лога. Регулярки записаны литералами, без `{10}`, поэтому работают и со старым mawk из Debian 12 и Ubuntu 22.04.

## Требования

Linux: Debian/Ubuntu, RHEL-семейство (Rocky, Alma, CentOS Stream, Fedora), а также Alpine и Arch, где часть разделов может быть беднее. Скрипт не POSIX-совместим и на macOS/BSD не запустится: он опирается на GNU/Linux-утилиты (`date -d`, `getent`, `findmnt`, `ss`, `df -T`, `/proc`). Нужны bash 4+, `curl`/`wget`, `tar` (для пунктов 6 и 7), `openssl` (для пункта 11). Желательно `timeout` из coreutils: им ограничены пункты 6, 7 и 11 (без него они просто работают без таймаута). Отдельные пункты сами подтянут нужные утилиты (`sysbench`, `nmap`, `globalping`, `iperf3`, `jq`) через тот пакетный менеджер, что нашёлся в системе: apt/dnf/yum/apk/pacman (и brew для globalping на macOS). Пункты 5 и 10 только читают систему; единственное исключение — установка или запуск fail2ban в пункте 10, и только после явного согласия. Для полной картины в Security Audit (чтение sshd_config, `sshd -T`, ufw/firewalld/iptables, systemctl) скрипт стоит запускать от root/через sudo.

## Отдельные команды: без vps-check

Любую проверку можно запустить отдельно, не скачивая этот скрипт. Номера совпадают с пунктами `vps-check`. Почти все эти команды запускают чужой код из интернета: на новом сервере сначала посмотри его (`curl -sL <ссылка> | less`). Форму `bash <(...)` используй там, где скрипту нужен терминал на вводе.

### Машина

**1. YABS: диск, сеть, Geekbench**

```bash
curl -sL yabs.sh | bash
```

**2. Bench.sh: CPU и диск**

```bash
wget -qO- bench.sh | bash
```

**3. sysbench: CPU в один поток и во все ядра.** Прирост во втором тесте должен быть близок к числу ядер. Если он заметно меньше, возможен оверселлинг (или vCPU — это потоки SMT; это ориентир, а не приговор).


**6. Ookla Speedtest: ближайший сервер.** Официальный CLI без установки. Для ARM-серверов замени `x86_64` на `aarch64` или `armhf`, для 32-битных x86 — на `i386`.

**7. Ookla до российских серверов.** Тот же CLI, но сервер выбирается явно. Найти российские серверы в нужном городе (нужен `jq`) и проверить один из них:

```bash
curl -s "https://www.speedtest.net/api/js/servers?engine=js&search=Moscow&limit=20" \

```

**8. iperf3 до городов России (itdoginfo).** Без iperf3 и jq скрипт сразу выходит с ошибкой `Required command 'iperf3' not found`, поэтому сначала поставь их (на минимальных образах Debian/Ubuntu может не быть и `ping` — он в пакете `iputils-ping`). Если при установке iperf3 спросит, запускать ли его как службу, — отвечай «No»: для теста служба не нужна.

```bash
apt install -y iperf3 jq iputils-ping    # или dnf / yum / apk / pacman (там ping — в пакете iputils)
bash <(wget -qO- https://raw.githubusercontent.com/itdoginfo/russian-iperf3-servers/main/speedtest.sh)
```

**9. Nmap: режет ли хостер исходящие порты.** Примеры для SMTP (порт 25 на MX Google) и общей проверки через тестовую цель Nmap. Полный набор целей — в функции `cmd_nmap` скрипта. `open` — порт доступен, `filtered` — пакеты дропаются, `closed` — служба не слушает, но блокировки нет.

```bash
apt install -y nmap                  # или dnf / yum / apk / pacman
MX=$(getent ahostsv4 gmail-smtp-in.l.google.com | awk '{print $1; exit}')
nmap -Pn -n --host-timeout 20s -p 25 "${MX:-142.250.27.27}"
nmap -Pn -n --host-timeout 20s -p 22,80,443 45.33.32.156
```
